AWebShop — Professional Complete Development Prompt

1. PROJECT OVERVIEW

Build AWebShop, an online marketplace where users can buy and sell fully
functional websites.

Core goals: - Users can browse websites. - Registered users can buy and
sell websites. - Sellers can choose Safe (escrow) or Fast (direct)
sale. - AWC (AwebShop Coin) is the platform token. - Manual card
payments are used initially. - Payme, Hamkorbank, and other payment APIs
must be designed as future integrations, not implemented as live
gateways now. - Telegram Bot is used for verification, account recovery,
and important notifications. - Admins have a complete management panel
and terminal-style Admin Console. - The project must use one personal
JSON backend: backend.json, accessed through Node.js. - Do not use
PostgreSQL, Redis, Docker, or any other database. - Do not add
unnecessary frameworks or dependencies. - Frontend uses vanilla HTML,
CSS, and JavaScript. - Backend uses vanilla Node.js.

Important implementation rule: Do not claim a feature is implemented
unless the generated code actually implements it. Do not leave
disconnected UI buttons, pages, APIs, database models, or configuration
entries. Every retained feature must have a clear connection to the
frontend, backend, and backend.json where applicable.

10. SAFE / ESCROW TRANSACTION

Flow:

1.  Buyer starts purchase.
2.  Buyer pays according to the selected payment method.
3.  Payment is recorded as pending/manual verification.
4.  Admin verifies payment.
5.  Seller transfers the website to the Admin, for example through a
    GitHub repository transfer or another agreed delivery method.
6.  Admin verifies the website.
7.  Buyer confirms that the delivered website is correct.
8.  Admin releases the payment to the Seller.
9.  Listing is marked Sold/Completed and removed from active marketplace
    listings.

Statuses:

    pending
    paid
    transferred
    verified
    completed
    cancelled
    disputed
    refunded

Time limits: - Seller transfer: 7 days. - Verification: 3 days. -
Auto-release: 7 days when applicable. - Dispute response: 3 days. -
Refund processing target: 5 days.

Admin must be able to configure these limits.

------------------------------------------------------------------------

11. FAST TRANSACTION

Flow:

1.  Buyer pays Seller directly.
2.  Seller delivers the website directly.
3.  Buyer confirms completion when applicable.
4.  Listing is marked sold.
5.  Listing is removed from active marketplace listings.

Fast transactions have fewer protections than Safe transactions. The UI
must clearly explain this difference.

34. MANUAL PAYMENT FLOW

Current payment system is manual.

Example flow:

1.  User selects top-up/purchase.
2.  System shows active Admin-configured payment card.
3.  User makes payment manually.
4.  User submits payment confirmation/proof through the supported
    interface.
5.  Admin reviews it.
6.  Admin approves or rejects.
7.  Transaction status updates.
8.  AWC or purchase state updates.
9.  Telegram notification is sent when applicable.

Payment API integration is future functionality.

Do not pretend manual payments are automatically verified.

Build AWebShop as a lightweight, maintainable website marketplace.

future API integrations. - Functional Admin panel. - Functional Telegram
verification/recovery/notifications. - Manual payments now, automated
payment APIs later. - Exactly 4 Premium plans. - Dynamic USD/UZS
conversion. - Responsive design. - English + Uzbek. - UZS + USD.

Do not add technologies or files merely to make the project look more
advanced. If a feature is not required, remove it. If two existing
features are disconnected but can logically be integrated, connect them
instead of duplicating the system.

The result must be a coherent, production-oriented AWebShop architecture
rather than a collection of unrelated pages and APIs.
